# twk: reference

The widget layer for terminal UIs in Dart, on top of
[twk_core](../../twk_core/README.md), the rendering core in
`packages/twk_core` of this repository (and `package:meta` for the
framework's annotations): every topic, widget and parameter, how the
package is tested, and its demos. The package's
[README](../README.md) is the short introduction.

`lib/twk.dart` exports one library per topic, `lib/src/<topic>/<topic>.dart`,
each with a doc comment naming what it is for. Widgets lay out and paint
through the core's render tree
([§1.8](../../twk_core/doc/design.md#18-flutter-like-layer) of its README); a topic's
tests are in `test/<topic>/`. Those that check what reaches a terminal
feed it to the emulator of [twk_test](../../twk_test/README.md), a dev
dependency by path: `package:twk_test/vt.dart`, and `VtTerminal`
(`package:twk_test/vt_terminal.dart`) for an app in the inline mode. Those
of every topic but the framework, foundation, style and text, and those of
the demos (`test/example/`), run apps with its `testTwk`: keys and mouse
reports go in as the bytes a terminal sends, through the core's parser,
under a fake clock, and the screen is read back through the emulator.

An app imports `package:twk/twk.dart` and no library of twk_core: besides
the topics, that library exports the declarations of twk_core that the API
here takes and returns, those a render object of an app's own is written
with, and a terminal in memory for tests. The render objects the widgets
create and the parent data they put on them, the frame loop and the
terminal's machinery stay in `package:twk_core`; the library comment of
`lib/twk.dart` gives the rule. `log` is also a function of `dart:math`
and `dart:developer`: an app that imports either prefixes it.

Two libraries of the package are not in `lib/twk.dart`, so that an app
that uses neither carries neither: `package:twk/hooks.dart`, hooks in the
flutter_hooks style ([below](#hooks-packagetwkhooksdart)), and
`package:twk/provider.dart`, Provider's API
([below](#provider-packagetwkproviderdart)), on which
[twk_bloc](../../twk_bloc/README.md) builds. An app that uses one imports it
besides `package:twk/twk.dart`; each builds on twk's public API alone,
its sources in `lib/src/hooks/` and `lib/src/provider/`, its tests in
`test/hooks/` and `test/provider/`, its example in `example/hooks/` and
`example/provider/`.

The package builds for the web with dart2wasm, where
[twk_web](../../twk_web/README.md) runs an app on xterm.js: what it takes
from dart:io goes through `lib/src/platform/`, as the core's does
([§1.7](../../twk_core/doc/design.md#17-terminal-and-platforms)), and there the
environment is empty, so `TWK_DEBUG` and `TWK_SCREEN_READER` turn
nothing on, a `FilePicker` lists nothing (`cannot list: no file system
on the web`) and finds no path, a `DirectoryTree` shows `(no file
system on the web)` below its root, the console's `save` fails with an
`UnsupportedError`, and a `WidgetError` shows no source.
`test/platform/web_check_test.dart` builds an app with `runApp` there and
runs it in node (`tool/web_check.dart twk`).

[SKILL.md](../SKILL.md) is a skill for coding agents that build apps with
twk: the mental model, setting an app up, the widgets by need, recipes,
tests with twk_test, debugging and the pitfalls.
`test/skill_test.dart` writes its code blocks into a package of their
own, which must analyze, format and pass its tests as written, checks
that every name its prose gives is exported, and that its pitfalls are
what twk does.

## Hooks: `package:twk/hooks.dart`

Hooks in the style of flutter_hooks: state, effects, memoized values,
listenables, streams, futures, animations and controllers that a build
keeps by calling functions, in place of the fields, `initState`,
`didUpdateWidget` and `dispose` of a `State`. `lib/hooks.dart` is a
library of its own, over `lib/src/hooks/`, which `lib/twk.dart` does not
export: an app that uses hooks imports it besides `package:twk/twk.dart`,
and one that does not carries none of it. It builds on twk's public API
alone.

```dart
import 'package:twk/hooks.dart';
import 'package:twk/twk.dart';

Future<void> main() => runApp(const Counter());

final class Counter extends HookWidget {
  const Counter({super.key});

  @override
  Widget build(BuildContext context) {
    final count = useState(0);
    return KeyBindings({
      'up': () => count.value++,
      'q': () => AppBinding.of(context).quit(),
    }, child: Text('Count: ${count.value}'));
  }
}
```

`dart run example/hooks/counter.dart` runs that counter in a box
(`--inline` below the shell's history).

### Widgets and rules

A `HookWidget` is a `StatelessWidget` whose `build` calls hooks; the
state of a `StatefulHookWidget` calls them in its `build`, besides what a
`State` keeps (its hooks are deactivated and disposed before it,
activated after it); `HookBuilder(builder:)` is a `HookWidget` written
in place. Another widget's element keeps hooks with the `HookElement`
mixin.

The element keeps the states of the hooks in the order its build called
them: the n-th hook of a build gets the state of the n-th hook of the
last one. So a build calls the same hooks in the same order every time,
none in a condition or a loop whose course changes, and calls them
itself, not in callbacks. In debug, a build that calls another hook
where its last build called one, or more or fewer hooks than it, fails
with an error naming the widget and the hooks (`HookBuilder called
useMemoized<int> as its hook 2, where its last build called
useState<int>: …`), shown in place of what it builds, and so does a hook
called by another hook's state; a hook called outside a build (in an
`initState`, a callback) is a `StateError` in release too. A hot reload
that changes the hooks a build calls fails so too, until a hot restart.
A build that threw before its last hooks calls them in the next one as
the first time.

### The hooks

A hook is made by the first build that calls it and disposed when the
element is unmounted, the last one first; one that takes `keys` is made
anew, the old one disposed first, when the keys of a build differ from
the last one's (`Hook.keysEqual`: by `==` item by item, a NaN equal to
itself).

| hook | gives |
|------|-------|
| `useState(initialData)` | a `ValueNotifier` whose changes rebuild the element |
| `useEffect(effect, [keys])` | nothing: runs `effect` in the first build, again where the keys change, in every build without keys, and the function it returned before each run and at unmount; within the build, so a change it makes to the state rebuilds nothing |
| `useMemoized(valueBuilder, [keys])` | what `valueBuilder` returned, until the keys change (without keys for good) |
| `useRef(initialValue)` | an `ObjectRef`, the same box in every build; its `value` changes rebuild nothing |
| `useCallback(callback, [keys])` | the callback of the first build, identical until the keys change |
| `useValueChanged(value, valueChange)` | null, then what `valueChange(oldValue, oldResult)` returned the last time `value` changed |
| `useContext()` | the context of the build, for functions that use hooks |
| `useListenable(listenable)` | the listenable, whose notifications rebuild the element; the listener goes over to the listenable of a later build |
| `useValueListenable(valueListenable)` | its value, rebuilt when it changes |
| `useValueNotifier(initialData, [keys])` | a `ValueNotifier` whose changes rebuild nothing |
| `useStream(stream, initialData:, preserveState: true)` | the latest `AsyncSnapshot` of the stream, as `StreamBuilder` builds from: waiting, active with each event, done; cancelled at unmount |
| `useFuture(future, initialData:, preserveState: true)` | the latest `AsyncSnapshot` of the future, as `FutureBuilder` builds from |
| `useAnimationController(duration:, reverseDuration:, initialValue:, lowerBound:, upperBound:, vsync:, keys:)` | an `AnimationController` ticking in the app's frames (or with `vsync`'s ticker), its durations those of the latest build |
| `useTicker(onTick)` | a `Ticker`, not started, calling the `onTick` of the latest build |
| `useFocusNode(debugLabel:, onKeyEvent:, canRequestFocus:, skipTraversal:, descendantsAreFocusable:)` | a `FocusNode` that each build sets up with these |
| `useFocusScopeNode(…)` | a `FocusScopeNode`, likewise |
| `useTextEditingController(text:, keys:)`, `.fromValue(value, [keys])` | a `TextEditingController`; the text of later builds is ignored |
| `useScrollController(initialOffset:, keys:)` | a `ScrollController` |
| `useListController(initialOffset:, keys:)` | a `ListController` |

When the stream or the future of a build is not the last one's, the hook
goes over to it, the snapshot kept, not connected, with `preserveState`,
or from `initialData` again without; the result of a future left, or of
one the element was unmounted with, is ignored.

A hook of one's own is a function that calls others, or a `Hook` (its
`keys`, its `debugLabel` for errors, `createState`) and its `HookState`,
put to work by `use(hook)`: `initHook` at the first use, `didUpdateHook`
with each later build's hook (not when a build gives the very same),
`build` for the value on every build, `deactivate`, `activate`,
`dispose`, `setState` to rebuild the element, and `debugFillProperties`
for the element's description, where `useState`, `useValueNotifier`,
`useStream`, `useFuture` and `useAnimationController` show their values
(`useState<int>: 3`).

## Provider: `package:twk/provider.dart`

[Provider](https://pub.dev/packages/provider)'s API: values provided to a
subtree and found by their type, the widgets that watch them rebuilt
when they change, and only those. `lib/provider.dart` is a library of its
own, over `lib/src/provider/`, which `lib/twk.dart` does not export: an
app that uses providers imports it besides `package:twk/twk.dart`. It is
built on twk's own `InheritedWidget`, `Listenable` and `ChangeNotifier`,
through twk's public API alone.

package:provider itself cannot be a dependency: its pubspec (6.1.5+1)
declares `environment: flutter: ">=1.16.0"` and depends on
`flutter: sdk: flutter`, besides `collection` and `nested`, so it resolves
only in a Flutter app. This library gives the same names and semantics
for twk apps instead.

[twk_bloc](../../twk_bloc/README.md) builds on it, as flutter_bloc does on
provider: its `BlocProvider` and `RepositoryProvider` are
`InheritedProvider`s, its Multi widgets `MultiProvider`s and its
`BlocListener` a `SingleChildStatefulWidget`, and its blocs are found
with this library's `context.read`, `watch` and `select`, which it
exports. A file imports both without a conflict.

```dart
import 'package:twk/provider.dart';
import 'package:twk/twk.dart';

Future<void> main() => runApp(
  ChangeNotifierProvider(create: (_) => CounterModel(), child: const Counter()),
);

class CounterModel extends ChangeNotifier {
  var _count = 0;

  int get count => _count;

  void increment() {
    _count++;
    notifyListeners();
  }
}

final class Counter extends StatelessWidget {
  const Counter({super.key});

  @override
  Widget build(BuildContext context) => KeyBindings(
    {
      'up': () => context.read<CounterModel>().increment(),
      'q': () => AppBinding.of(context).quit(),
    },
    child: Consumer<CounterModel>(
      builder: (context, counter, _) => Text('Count: ${counter.count}'),
    ),
  );
}
```

`dart run example/provider/counter.dart` (or with `--inline`) runs it in
a rounded box, the count shown by a widget that selects it
(`context.select<CounterModel, int>((c) => c.count)`);
`test/provider/example/counter_test.dart` tests it.

### Providing

Each provider creates its value the first time it is read, unless
`lazy: false` (then when it is placed in the tree), with the provider's
context, in which `create` may read the providers above (`context.read`,
one of its own type too) but not depend on them: that fails an assert.
It disposes of what it created when it leaves the tree, and of nothing
it was given (`.value`). A `.value` provider given a new value that is
not `==` the old one (or as `updateShouldNotify` says) rebuilds the
widgets that watch it. Each takes a `child`, or a `builder:
(context, child) => …` whose context is below the provider; one of the
two outside a `MultiProvider`.

| provider | provides |
|----------|----------|
| `Provider<T>(create:, dispose:, lazy:)`, `Provider.value(value:, updateShouldNotify:)` | A value. One that is a `Listenable` or a `Stream` fails an assert, since its changes would rebuild nothing (`Provider.debugCheckInvalidValueType = null` allows it) |
| `ChangeNotifierProvider<T>(create:)`, `.value(value:)` | A `ChangeNotifier`, whose notifications rebuild the widgets that watch it; disposed when it was created |
| `ListenableProvider<T>(create:, dispose:)`, `.value(value:)` | Any `Listenable`, as above; listened to from its first read until it is replaced or the provider leaves the tree |
| `ValueListenableProvider<T>.value(value:, updateShouldNotify:)` | The value of a `ValueListenable<T>`, found as a `T` |
| `FutureProvider<T>(create:, initialData:, catchError:)`, `.value(value:, …)` | `initialData`, then what the future completes with; an error is what `catchError` returns for it, else logged at `LogLevel.error` while the value stays. `.value` listens at once |
| `StreamProvider<T>(create:, initialData:, catchError:)`, `.value(value:, …)` | `initialData`, then each value of the stream that is not `==` the last; cancelled when the provider leaves the tree |
| `ProxyProvider<T, R>(update: (context, t, previous) => …, create:, dispose:)`, `ProxyProvider2<T, T2, R>`, `ProxyProvider0<R>` | What `update` makes from the providers above and the value it made before (`create`'s, or null, the first time), made anew when they change or the widget is replaced: a value not `==` the one before rebuilds the watchers, and the old one goes to `dispose` |
| `InheritedProvider<T>(create:, update:, startListening:, dispose:)`, `DeferredInheritedProvider<C, T>` | What the others are made of, for providers of one's own |

`MultiProvider(providers: [Provider(create: …), …], child:)` nests the
providers, the first outermost, each given without a child; it takes a
`builder` too, and one MultiProvider may be in the list of another. What
it nests are `SingleChildWidget`s: `SingleChildStatelessWidget`,
`SingleChildStatefulWidget` with its `SingleChildState`, and
`SingleChildBuilder`, as package:nested has them.

### Finding

- `context.read<T>()`: the nearest provided `T` without depending on it,
  for callbacks and `initState`.
- `context.watch<T>()`: the same, and the widget is rebuilt each time it
  changes, as long as its builds watch it.
- `context.select<T, R>((t) => …)`: what the selector picks, and the
  widget is rebuilt only when a change makes it pick something else: not
  `==`, lists, sets, maps and other iterables compared element by element.
  A build may select any number of parts; what earlier builds selected is
  forgotten. Reading, watching or selecting in a selector fails an assert.
- `Provider.of<T>(context, listen:)`: `watch` when `listen`, else `read`.

A provider is found by the type it provides: a `Provider<Counter>` by
`read<Counter>()`, the nearest hiding those above. None found is a
`ProviderNotFoundException` naming the type and the widget, unless the
type is nullable: `read<Counter?>()` is then null. A `Provider<int?>` is
found by `read<int>()` too, its null a `ProviderNullException`.

### Building

| widget | does |
|--------|------|
| `Consumer<T>(builder: (context, t, child) => …, child:)` | Builds with the value, again each time it changes; the widgets around it are not rebuilt, and `child` is built once, by the parent |
| `Consumer2<A, B>` | The same with two values |
| `Selector<A, S>(selector: (context, a) => …, builder: (context, s, child) => …, shouldRebuild:)`, `Selector2`, `Selector0` | The selector runs by each change; the builder only when it picks something else (compared as `select` compares, or as `shouldRebuild` says) or the widget is replaced |

### On twk's framework

A provider is an `InheritedWidget` whose element (a subclass of twk's
`InheritedElement`) keeps the value and calls `notifyClients` in its own
build when the value changes. twk has none of Flutter's `InheritedModel`
aspects (`dependOnInheritedElement` takes no aspect, and an inherited
element keeps no data per dependent), so `select` keeps its own: the
element holds, for each dependent, whether it watched the whole value,
else the selectors its last build registered, and its `notifyDependent`
runs them before it rebuilds the dependent. A dependent's selectors are
those of its last build, told apart by the owner's rebuild count
(`BuildOwner.rebuilds`), which each build of an element moves on; one
that watched once stays told of every change, as with package:provider.

twk drops a dependency that a build does not register again; the element
keeps those `update` registered through the builds that do not call it
(a listenable's notification), as Flutter would. Its own lookups start
at its parent, so that `create` and `update` find the providers above.

### Unlike package:provider

- `watch` and `select` outside a build (from a key handler) are not
  refused: twk has neither `Element.debugDoingBuild` nor
  `BuildOwner.debugBuilding`. The dependency made lasts until the next
  build of the widget. `read` in a build is allowed, as in provider 6.
- Not here: `ChangeNotifierProxyProvider`, `ListenableProxyProvider`,
  `ProxyProvider3` to `6`, `Consumer3` to `6`, `Selector3` to `6`,
  `ReassembleHandler` and the devtools binding.
